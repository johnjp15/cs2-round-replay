# 3D CS2 simulator: plan and task board

Written by the orchestrator (Fable 5.1) on 2026-11-07 from John's request:

> Leave the 2D sim as its own web app, but create a new one in 3D that copies as much of CS2's physics as possible, exactly. The graphics don't need to be realistic, but should be low fidelity at least with the right colors. Make it a generic CS2 simulator game that works for any scenario, then load the round info into this 3D game and make sure we can play it just like the 2D one, except with full 3D controls and gun aiming.

Opus 5.5 agents implement it, one task card each. The 2D app (`src/app`, `src/sim2d`, published at `cs2/sim/`) stays as it is and keeps working.

## Decisions (fixed unless John says otherwise)

1. **Same repo, second app.** The 3D game lives here as `src/sim3d` (the engine: an `IHost`) and `src/app3d` (Three.js view, first-person controls, HUD), published at **`https://johnjp15.github.io/cs2/sim3d/`** behind the same lock. The Core (`src/core`: puppets, scripted events, divergence, rejoin, takeover, checkpoints, summary) and the contracts are shared unchanged: the Core never knew it was driving a 2D host, and the 3D host is exactly the kind of second host the contracts were designed for (the third is the CS2 server adapter). Anything that would fork the Core is a bug.
2. **No physics library.** CS2's player movement is Source's bespoke movement code (categorize position, try-player-move, step-move, gravity, air accelerate, duck, jump, stamina), already implemented in 3D on the CS2 collision mesh in `src/sim2d/movement.ts` + `geometry.ts` (G3, `docs/movement.md`). The 3D engine reuses it and extends it (ladders, water are out of scope for now). Weapons are hitscan with CS2's spread/recoil/inaccuracy model, grenades are Source projectiles.
3. **Rendering: Three.js**, flat shading, no textures except the radar: upward faces take the colour of the CS2 radar image under them (radar transform `px = (x − pos_x) / scale`, `py = (pos_y − y) / scale`), vertical faces a per-map palette (Mirage: sandstone, with the wooden crates, blue doors and dark Apartments interiors approximated from the radar colour of the nearest floor and height), undersides dark. Players are capsules in team colours (T yellow-orange, CT blue; the human's teammates with name tags), simple box viewmodel, tracers, muzzle flash, blood-free hit marker. 60 fps on an M-series Mac; phones spectate.
4. **Generic first, Mirage second.** The engine loads a *map package* (collision mesh, player clips, CS2 nav, radar + `map_data` transform, bomb sites, spawns) produced by the existing tools from any **awpy-data** map, and a *scenario* (start state for N players, round rules, optional recording = the existing `round.json` shape). The Mirage round is one scenario. A scenario without a recording is **free play**: every bot is LIVE from the first tick.
5. **Same features as the 2D app** once loaded with the round: watch mode by default, E takes control of cart, rewind/seek/speed, end-of-round summary vs the recording, timeline, radar minimap, aiDebug. Plus 3D: pointer-lock mouse look, WASD, Space, Ctrl (duck), Shift (walk), mouse 1 fire, R reload, 1–5 weapon slots, G drop, E use (plant/defuse/takeover), grenades (throw with mouse 1, underhand with mouse 2).
6. **Determinism and portability stay.** The engine is deterministic by seed (spread/recoil use the seeded RNG the Core already relies on), runs headless in Node for tests and the harness, and keeps `docs/conventions.md`. The golden-master idea applies: with no human, the 3D host must reproduce the recording exactly (9 kills, plant 1761, defuse 3955→4275, "Played it like the tape"), since it drives the same puppets along the same snapped tracks with the same scripted damage.
7. **Shared engine code.** Modules in `src/sim2d` that are already 3D-correct (geometry, movement, bomb, round rules, weapons/damage tables, grenades) are imported by `src/sim3d` for now (ESLint: `sim3d` may import `sim2d` and `contracts`; `app3d` may import anything). Pure new modules that both hosts could use go in `src/engine/` (imports only `contracts`). Moving the shared modules out of `sim2d` into `engine` is a later refactor, after G5/G6 land, not now.

## Architecture

```
src/contracts : Observe / Act / Control, IHost, ICore, round data, tuning, summary        (shared, unchanged)
src/core      : clock, schedule, puppets, scripted, divergence, rejoin, takeover, checkpoints, summary   (shared, unchanged)
src/engine    : pure CS2 game-mechanics modules usable by any host: weapons (stats, spread, recoil, damage, penetration), hitboxes, rng   (H2)
src/sim2d     : the 2D host (unchanged; sim3d imports its 3D-correct modules: geometry, movement, bomb, round, weapons, grenades)
src/sim3d     : the 3D host (IHost): world (map package), pawns with 3D view angles and hitboxes, hitscan with spread/recoil, grenades, sight (eye traces on the mesh), hearing, LIVE AI on the CS2 nav mesh, headless harness   (H1, H3)
src/app3d     : Three.js renderer, pointer-lock controls, HUD, radar, takeover, rewind/seek/speed/summary UI, embedded assets, single-file build   (H1, H4)
tools         : map package builder for any awpy-data map (extract-geometry/clips/snap-tracks generalized), scenario validation, 3D harness   (H3)
data/maps/<map>/ : map packages;  data/scenarios/<name>.json : scenarios (the Mirage round = data/scenarios/mirage-sp4rtan-1v3.json → data/round.json)
```

The Core ↔ host contract is per tick: host `observe()` → Core `step(observe)` → `Act` → host `apply(act)`; `tick()`. `PawnObs` carries pos (x, y, z), yaw, pitch, vel, crouching, onGround, hp, armor, weapon, sees, sounds; `Act` carries inputs (forward/side/buttons/yaw/pitch), set_weapon, block_damage, damage, set_mode, teleport, set_round, strip, log (see `docs/contracts.md`). The 3D host maps pitch to real vertical aim (Source convention, + = down).

### H2 · CS2 weapon mechanics, exact (Opus 5.5; pure module, parallel with H1)
- `src/engine/weapons/`: a data table for every CS2 weapon (`data/weapons.json`): damage, armor penetration, range modifier (damage falloff per 500 u), cycle time (fire rate), clip and reserve, reload time, draw time, max player speed and scoped speed, headshot multiplier, hitgroup multipliers, penetration power, inaccuracy stand/crouch/move/jump/fire/ladder, recoil angle/magnitude/variance, spread, recovery time stand/crouch, bullets per shot (shotguns), tagging; plus the **recoil patterns** (the per-shot sprays of the AK-47, M4A4, M4A1-S, Galil, FAMAS, AUG, SG 553, MP9, MAC-10, UMP, P90, Bizon, MP7, MP5-SD, Negev, M249) as data, and the inaccuracy model: how spread + inaccuracy combine into the shot direction (Source's `GetSpread`/`GetInaccuracy` logic: two random angles/radii with the weapon's seeded RNG; the sim is deterministic by seed), movement inaccuracy scaling with speed relative to max speed, jumping, "accuracy recovery" after moving, the fire-rate-driven inaccuracy accumulation and decay, aim punch (view kick) from recoil and from being hit, and tagging (velocity reduction when hit). Scoped weapons (AWP, SSG 08, SG 553/AUG): scoped inaccuracy and speed, unscoped inaccuracy.
- Sources: CS2's game files (`items_game.txt` / weapon vdata) as mirrored in public GitHub repos, the public Source SDK 2013 (`cs_weapon_parse`, `weapon_csbase`), Valve's blog and release notes for CS2 changes; cite every number's source in `docs/weapons.md`; mark unverified numbers as such and keep them in `data/tuning.json` → `weapons` as tunables.
- Damage: keep the existing CS2 damage math from `src/sim2d/weapons.ts` (it reproduces every recorded hit) but generalize it to the table; wall penetration (`docs/combat.md` follow-up) as a function of penetration power and the mesh thickness along the ray, with the Source damage reduction formula, documented and tested on the Mirage mesh (e.g. the B Apartments window frame, the Shop door).
- Tests: per-weapon tables load; AK-47 first-shot spread and spray pattern reproduce the known values; damage falloff at 500/1000 u; armor math vs the recorded hits (73 HP / 7 armor SSG 08 on cart with 100 armor; 27/34/26 AK hits on donk); deterministic per seed.
- Ownership: `src/engine/weapons/**`, `data/weapons.json`, `docs/weapons.md`, tests. Nothing else. H1 integrates it into the 3D hitscan after both land (or H4 does).

### H3 · Generic maps and scenarios, free play, LIVE AI on the CS2 nav (Opus 5.5; after H1)
- `tools/build-map.ts <map>`: downloads the awpy-data release assets for `<map>` (mesh, nav, radar, map_data) with checksums into `data/source/cs2/<map>/`, builds the map package `data/maps/<map>/` (G2GM mesh, clips from the CS2 nav flood (G3's `extract-clips` generalized), radar + transform, bomb sites and spawns from the nav's place names / `.nav` attributes, height map). Mirage is rebuilt through this path and must be byte-identical to today's data.
- Scenario format `data/scenarios/<name>.json`: map, rules (c4 timer, freeze time, round time, score), players (team, name, start pos/yaw, hp, armor, helmet, kit, weapons/ammo, grenades, money), optional recording (= `round.json` content or a path). The Mirage round becomes `data/scenarios/mirage-sp4rtan-1v3.json`; a second scenario (e.g. a 5v5 Mirage free-play start, or de_dust2 if awpy has it) proves generality.
- LIVE AI generic: pathfinding on the CS2 `.nav` (areas, connections, ladders/jump links where the nav marks them), roles from the scenario (hold, rotate, take site, plant, guard, retake, defuse, hunt) with site/spawn knowledge from the map package; the existing Mirage 2D-grid nav stays for the 2D app.
- Free play: no recording, everyone LIVE, the human on any team/pawn, a scenario picker and map picker in the 3D app's panel.
- Acceptance: Mirage package byte-identical; the round scenario plays exactly as before; a second map loads and bots path across it; free play on Mirage ends in a normal round end; docs `docs/maps.md`, `docs/scenarios.md`, `docs/ai.md` additions.

### H4 · Parity and polish (Opus 5.5; after H1–H3)
- Everything the 2D app has: rewind/seek with the input tape, checkpoints, summary overlay vs the recording, timeline scrubber, aiDebug, Safari/iPhone spectate check, performance (256 ticks/s at 4×), the locked page size, the follow-recording run in 3D with G5's duel rules (tape-identical input → the tape), G6's sight parity, spectator cameras, settings (sensitivity, FOV, crosshair), a sound-free "footstep/shot" visual cue. Playtest doc.

**The fidelity bar (John, 2026-11-07 03:23):** "good enough for a seasoned CS2 player to not be able to tell the difference in movement and shooting mechanics — 95 % of the way there." **Competitive-mode CS2 defaults only, never KZ values**: KZ (sv_airaccelerate 100+, auto-bhop, enablebunnyhopping) is a different game; at stock values pre-strafing gives next to nothing and chaining strafed long jumps is not realistically possible. Air strafing, a single strafed jump, crouch-jumps, counter-strafing and the landing clamp are stock behaviour and must match.

## What stays true for the CS2 port

The Core and contracts are untouched. Everything 3D-specific the host does (view angles, hitboxes, spread, penetration, nav pathing) maps to what the CS2 server provides natively (the engine's usercmds, hitboxes, weapon code, traces, nav mesh); `docs/port-notes.md` keeps the mapping table.
